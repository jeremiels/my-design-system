# Créer un design system de marque

Le socle (`my-design-system`) fournit des composants génériques, leurs tokens `--u-*` et l'outillage pour les étendre. Un design system de marque **dépend** du socle, l'**étend** (thème, composants modifiés, composants propres) et **republie** le tout sous son propre package, que les applications de la marque consomment. Le modèle est décrit dans l'[ADR 0001](?path=/docs/documentation-adr-0001-architecture-multi-marque--docs).

Un exemple complet et testé se trouve dans `examples/acme-design-system`. `npm run example` construit le socle, l'empaquette avec `npm pack` comme pour une publication, puis installe, construit et teste ACME contre cette archive.

## 1. Dépendances

```json
{
  "dependencies": { "my-design-system": "^0.1.0" },
  "peerDependencies": { "lit": "^3.3.3" }
}
```

Lit est une **peer dependency** du socle comme de la marque : l'application en fournit une seule copie.

## 2. Build

Le socle compile les imports `with { type: "css" }` avec un plugin Vite qu'il exporte. La marque l'utilise, et laisse Lit et le socle en dépendances au lieu de les embarquer :

```ts
// vite.config.ts
import { cssImportAttributes } from "my-design-system/vite-plugin";

export default defineConfig({
  plugins: [cssImportAttributes()],
  build: {
    lib: {
      entry: {
        index: "src/index.ts",
        define: "src/define.ts",
        styles: "src/styles.css",
        reset: "src/reset.css",
      },
      formats: ["es"],
    },
    rolldownOptions: { external: [/^lit/, /^my-design-system/] },
  },
});
```

- Types des imports CSS : `/// <reference types="my-design-system/css-modules" />` dans un fichier `.d.ts`.
- `tsconfig.json` : `experimentalDecorators: true` et `useDefineForClassFields: false`, comme dans le socle (décorateurs de Lit).

## 3. Thème

Une marque change les **valeurs** des tokens, jamais leurs noms. Ses valeurs vivent dans un sous-layer `u.tokens.brand`, déclaré après ceux du socle :

```css
/* src/theme.css */
@layer u.tokens.brand {
  :root {
    --u-color-primary: hsl(268, 75%, 45%);
    --u-font-family-base: Georgia, serif;
  }
}
```

```css
/* src/styles.css : la feuille que chargent les applications */
@import "my-design-system/styles.css";
@import "./theme.css";
```

L'ordre des imports compte : un sous-layer déclaré avant ceux du socle passerait **sous** eux. Les valeurs du mode sombre se redéfinissent aux deux mêmes endroits que dans le socle (voir l'exemple). **Toute primitive que la marque redéfinit doit avoir sa valeur sombre :** le layer de la marque l'emporte aussi sur les valeurs sombres du socle, si bien que sa valeur claire resterait en mode sombre, à côté du texte sombre du socle. La production des tokens depuis Figma fera l'objet d'un ADR dédié.

- **Plusieurs marques sur une page :** le thème s'applique à un conteneur plutôt qu'à `:root` (`[data-brand="acme"] { --u-color-primary: … }`). L'attribut `data-brand` est nécessaire : c'est sur lui que le socle redéclare ses tokens sémantiques, pour qu'ils suivent les primitives du conteneur.
- **Contraste :** les valeurs par défaut du socle respectent WCAG AA. Une marque qui change les couleurs doit garder, dans les deux thèmes, un contraste de 4,5:1 entre chaque fond et son texte, et de 3:1 pour l'anneau de focus. `contrastFailures()` les mesure dans le navigateur, sur les couleurs calculées, et renvoie les paires sous leur minimum. Le socle l'utilise pour ses propres tokens, et l'exemple pour ceux d'ACME :

  ```ts
  import { contrastFailures } from "my-design-system/testing";

  for (const theme of ["light", "dark"]) {
    document.documentElement.dataset.theme = theme;
    expect(contrastFailures()).toEqual([]);
  }
  ```

  Pour un thème appliqué à un conteneur : `contrastFailures(conteneur)`. Pour les composants propres à la marque : `contrastFailures(document.body, [...contrastPairs, { foreground, background, minimum }])`.

- **Reset :** `my-design-system/reset.css` est optionnel. Pour que les applications ne dépendent que de la marque, elle le republie (`src/reset.css` : `@import "my-design-system/reset.css";`).

## 4. Étendre un composant du socle

```ts
import { Button } from "my-design-system";
import acmeButtonStyles from "./acme-button.css" with { type: "css" };

export class AcmeButton extends Button {
  static styles = [Button.styles ?? [], acmeButtonStyles];
}
```

La feuille de la marque s'ajoute à celle du socle. Elle peut changer la valeur par défaut d'un token de composant sur `:host` (`--u-button-border-radius: var(--u-radius-full)`), ou celle d'une variante sur `:host([variant="secondary"])`, comme le socle, ou styler les éléments internes **par leurs parts** :

```css
/* acme-button.css */
[part~="button"] {
  text-transform: uppercase;
}
```

Seule l'API documentée du socle est stable : tokens, parts, slots et membres `protected` documentés. Les parts sont vérifiées par le test de contrat du socle ; ses classes CSS (`.button`) sont internes et peuvent changer sans préavis.

## 5. Ajouter un composant de marque

```ts
import { Button, DSBaseElement } from "my-design-system";
import { html } from "lit/static-html.js";

export class AcmeCard extends DSBaseElement {
  static override componentName = "card";
  static override dependencies = [Button];

  render() {
    const button = this.tagFor(Button);
    return html`<article><slot></slot><${button}>Action</${button}></article>`;
  }
}
```

- `componentName` donne la balise : `acme-card`.
- Un composant qui en rend un autre le déclare dans `dependencies` et passe par `tagFor()` : la carte rend ainsi le bouton **de la marque**. Jamais de balise écrite en dur, ni de `document.createElement`.
- Ses tokens prennent le préfixe de la marque (`--acme-card-padding`), et sa JSDoc suit les mêmes conventions que le socle (`@element`, `@csspart`, `@cssprop`…).
- **Nom de composant :** si le socle ajoute plus tard un composant du même nom (`card`), `defineComponents()` lèvera une erreur à l'enregistrement, puisque `AcmeCard` ne l'étend pas. Vérifier les nouveautés du catalogue à chaque montée de version du socle ; un nom propre à la marque évite la question.

## 6. Enregistrer et republier

```ts
// src/define.ts : les applications l'importent une fois
import { allComponents, defineComponents } from "my-design-system";

defineComponents({
  prefix: "acme",
  components: [...allComponents, AcmeCard],
  overrides: { button: AcmeButton },
});
```

```ts
// src/index.ts : le socle republié avec les composants de la marque
export * from "my-design-system";
export * from "./components/acme-button/acme-button.js";
export * from "./components/acme-card/acme-card.js";
```

- `overrides` remplace un composant **partout** dans l'enregistrement : `acme-modal` et `acme-card` rendent `AcmeButton`.
- Si deux applications d'une même page (micro-frontends) embarquent chacune le design system de marque, le second enregistrement ne casse rien : les balises déjà définies gardent leur définition, avec un avertissement en console si elle diffère (autre version). Les deux applications utilisent alors la version chargée en premier : mieux vaut partager une seule copie.
- Le package déclare `"sideEffects": ["**/*.css", "./dist/define.js"]`, pour que les applications ne chargent que les composants qu'elles utilisent.

## 7. Documentation

Le manifest de la marque inclut celui du socle (`dependencies: true` dans `custom-elements-manifest.config.mjs`) : les composants qui étendent le socle sont documentés avec ce dont ils héritent (attributs, tokens, parts).
