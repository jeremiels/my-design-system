# Architecture CSS

Ce document décrit l'architecture CSS utilisée dans ce projet, en mettant l'accent sur la modularité, la maintenabilité et l'évolutivité. L'architecture est conçue pour faciliter la collaboration entre développeurs et assurer une approche cohérente du style dans l'application.

## Les Couches (Layers)

Le CSS global (hors shadow DOM) est organisé en couches, toutes rangées sous la couche `u`, de la moins à la plus prioritaire :

1. **`u.reset`** : une réinitialisation CSS moderne pour assurer une base cohérente entre les navigateurs.
2. **`u.tokens`** : jetons de design pour les couleurs, la typographie, l'espacement, etc.
3. **`u.base`** : styles de base pour les éléments HTML (par exemple, titres, paragraphes, liens).
4. **`u.components`** : styles globaux visant les composants depuis la page (par exemple, l'espacement entre eux). Leurs styles internes vivent dans leur shadow DOM, que les couches de la page n'atteignent pas.
5. **`u.utilities`** : classes utilitaires pour les motifs de style communs (par exemple, `.visually-hidden`).
6. **`u.shame`** : une couche spéciale pour les surcharges d'urgence avec `!important`. Cette couche doit être:
   - Utilisée en dernier recours uniquement
   - Documentée de manière exhaustive
   - Maintenue au minimum absolu
   - Accompagnée d'un plan pour supprimer ces surcharges

## L'API @layer

L'API `@layer` est une fonctionnalité puissante de CSS qui nous permet de déclarer explicitement des "couches en cascade" et de contrôler leur ordre de priorité. L'ordre est déclaré une seule fois, dans `src/styles/layers/order.css` :

```css
@layer u.reset, u.tokens, u.base, u.components, u.utilities, u.shame;

@layer u.reset {
  /* Styles de réinitialisation */
}
```

**Pourquoi le préfixe `u` :** les noms de couches sont globaux au document. Des noms nus (`base`, `utilities`…) fusionneraient avec les couches de l'application hôte — Tailwind CSS v4, par exemple, déclare `theme, base, components, utilities`. C'est le même raisonnement que le préfixe `--u-` des tokens ([ADR 0001](?path=/docs/documentation-adr-0001-architecture-multi-marque--docs), D4). Les styles de l'application hors couche restent prioritaires sur toutes les couches du socle.

### Deux feuilles : `styles.css` et `reset.css`

- **`my-design-system/styles.css`** (`src/styles/main.css`) : les tokens et les classes utilitaires, c'est-à-dire ce dont les composants ont besoin. Elle ne style aucun élément de la page : toute application peut la charger.
- **`my-design-system/reset.css`** (`src/styles/reset.css`), **optionnelle** : le reset et les styles de base, qui touchent toute la page (`body`, titres, médias, champs de formulaire, réduction des animations). À charger avec `styles.css`, dont elle utilise les tokens, sauf si l'application a déjà son propre reset.

Les deux importent d'abord `layers/order.css` : l'ordre des couches tient quel que soit l'ordre de chargement.

### Avantages de @layer

- **Contrôle de la Spécificité**: Les couches permettent de gérer la spécificité de manière plus prévisible
- **Organisation Claire**: Meilleure organisation du code avec une hiérarchie explicite
- **Maintenance Simplifiée**: Facilite la maintenance en isolant les styles par couche

### Organiser les Tokens avec @layer

Pour maintenir une architecture claire et scalable, chaque fichier de token doit déclarer sa propre couche `@layer`. Cette approche présente plusieurs avantages:

```css
/* src/styles/tokens/color.css */
@layer u.tokens.color {
  :root {
    --u-color-primary: hsl(210, 100%, 44%);
    --u-color-secondary: hsl(150, 100%, 26%);
    /* ... */
  }
}
```

```css
/* src/styles/layers/tokens.css - imports simplifiés */
@import "../tokens/color.css";
@import "../tokens/semantic.css";
@import "../tokens/spacing.css";
@import "../tokens/typography.css";
@import "../tokens/radius.css";
@import "../tokens/motion.css";
@import "../tokens/elevation.css";

/* Déclaration de l'ordre des sous-couches */
@layer u.tokens.color, u.tokens.semantic, u.tokens.spacing, u.tokens.typography,
  u.tokens.radius, u.tokens.motion, u.tokens.elevation;
```

**Avantages de cette approche:**

- **Auto-documentée**: Chaque fichier de token déclare clairement sa couche
- **Scalable**: Ajouter de nouveaux tokens ne nécessite que d'ajouter le fichier et l'import
- **Évite les imbrications**: Pas de `layer()` dans les imports évite les nids de couches invalides
- **Maintenance simplifiée**: La hiérarchie est explicite et centralisée dans `tokens.css`

### Les Trois Niveaux de Tokens (Primitif → Sémantique → Composant)

Pour que le système soit réellement themable, une seule source de vérité doit exister pour chaque valeur. Cela impose une hiérarchie stricte à trois niveaux, où chaque niveau ne référence que le niveau précédent — jamais de valeur littérale en dehors du niveau primitif :

1. **Primitif** (`src/styles/tokens/color.css`, `spacing.css`, …) — valeurs brutes de la marque (`--u-color-primary: hsl(210, 100%, 44%)`).
2. **Sémantique** (`src/styles/tokens/semantic.css`) — alias par intention, jamais par apparence (`--u-color-action-bg: var(--u-color-primary)`, `--u-color-danger-bg: var(--u-color-danger)`). Les états d'interaction (hover/active) sont dérivés avec `color-mix()` plutôt que codés en dur, pour n'avoir qu'une seule couleur à maintenir par intention. Ils tirent la couleur vers `--u-color-text`, l'opposé du texte inversé qu'elle porte : plus sombre en mode clair, plus claire en mode sombre, si bien que le contraste ne peut qu'augmenter.
3. **Composant** — chaque composant Lit déclare ses propres custom properties sur `:host`, dont la valeur par défaut pointe vers le token **sémantique** correspondant (jamais vers un token primitif ni une valeur littérale) :

   ```css
   :host {
     --u-button-background-color: var(--u-color-action-bg);
   }
   .button {
     background-color: var(--u-button-background-color);
   }
   ```

**Variantes et tailles :** elles changent la valeur par défaut des tokens de composant **sur l'hôte**, à partir de l'attribut reflété (`:host([variant="danger"]) { --u-button-background-color: var(--u-color-danger-bg); }`), et jamais sur un élément interne. Une valeur posée par l'application sur l'hôte, depuis l'extérieur du shadow root, l'emporte sur toute règle `:host(…)` ; redéclaré sur un élément interne (une classe `.button--danger`), le token écraserait au contraire la valeur de l'application, pour cette variante seulement. `src/api-contract.test.ts` refuse les deux cas.

**Pourquoi ce niveau intermédiaire est indispensable :** sans lui, changer `--u-color-primary` ne se propage à aucun composant, et le dark mode devrait être ré-implémenté dans chaque fichier de composant au lieu d'être remappé une seule fois au niveau primitif.

**Dark mode :** `tokens/color.css` remappe les primitives à deux endroits, jamais ailleurs — un composant ne doit donc jamais contenir sa propre logique de thème :

- `@media (prefers-color-scheme: dark)` sur `:root:not([data-theme="light"])` — bascule automatique selon la préférence OS de l'utilisateur.
- `:root[data-theme="dark"]` — bascule manuelle, pour un sélecteur de thème dans l'application consommatrice (ex. `document.documentElement.dataset.theme = "dark"`).

**Thème limité à un conteneur :** un `var()` est résolu sur l'élément qui déclare la custom property, puis hérité tel quel. Déclarés sur `:root` seulement, les tokens sémantiques garderaient les primitives de `:root`, même dans un conteneur qui les redéfinit. Ils sont donc déclarés sur `:root, [data-brand]` : un thème de marque appliqué à `[data-brand="acme"]` (plusieurs marques sur une page, ADR 0001, D4) atteint les composants de ce conteneur.

**Accessibilité :** `src/styles/tokens.test.ts` vérifie, dans les deux thèmes, que chaque intention (au repos, survol, pression) offre un contraste de 4,5:1 avec son texte (WCAG AA), le texte 4,5:1 avec les surfaces et l'anneau de focus 3:1. Les paires et la mesure sont exportées (`contrastFailures()`, `my-design-system/testing`) : une marque vérifie son thème avec les mêmes.

**Préfixe :** tous les tokens, des trois niveaux, portent le préfixe `--u-` ([ADR 0001](?path=/docs/documentation-adr-0001-architecture-multi-marque--docs), D4). Il évite les collisions avec les variables de l'application hôte ou d'autres librairies, et il est identique pour toutes les marques : une marque change les valeurs, jamais les noms.

**Convention de nommage des tokens de composant :** `--u-<composant>-<propriété-css>[-<état>]`, ex. `--u-button-background-color-hover`. `<composant>` est le nom du composant sans le préfixe de balise : `button`, que la balise soit `u-button` ou `acme-button`. Le nom de la propriété CSS ciblée (`background-color`, non `bg`) doit apparaître en toutes lettres pour rester non-ambigu à grande échelle.

**Documentation :** chaque token de composant est documenté dans la JSDoc de la classe : `@cssprop [--u-button-background-color=var(--u-color-action-bg)] - description`. Le Custom Elements Manifest (`npm run analyze`) les affiche dans Storybook, et `src/api-contract.test.ts` vérifie que les tokens documentés sont exactement ceux déclarés sur `:host`.

**Fichiers de styles :** les styles shadow DOM d'un composant (ou d'un mixin) vivent dans un fichier `.css` voisin (`alert.css` à côté de `alert.ts`), importé comme _CSS module script_ — jamais dans un template littéral Lit `css` inline :

```ts
import alertStyles from "./alert.css" with { type: "css" };

static styles = [DSBaseElement.styles ?? [], alertStyles];
```

L'import renvoie un `CSSStyleSheet` constructible, que Lit adopte directement. Vite ne supporte pas nativement `with { type: "css" }` : le plugin local `plugins/css-import-attributes.ts` le prend en charge (dev, Storybook, Vitest et build) et inline le CSS minifié dans le JS publié, le consommateur n'a donc rien à configurer.

### Prérequis : la feuille de tokens est une dépendance, pas une option

Les tokens de composant ci-dessus **n'ont pas de fallback littéral** (`var(--u-color-action-bg, #007bff)`). C'est un choix délibéré, pas un oubli :

- Un fallback littéral duplique la valeur qui existe déjà dans `tokens/`. Dès qu'un deuxième composant a besoin de la même couleur, on a deux sources de vérité qui peuvent diverger silencieusement — exactement le problème que les trois niveaux de tokens sont censés éliminer.
- La feuille de tokens est un point d'entrée séparé (`my-design-system/styles.css`, ou celle du design system de marque) que l'application charge une fois ; `src/index.ts` ne l'importe pas, pour rester sans effet de bord. C'est la même convention que Spectrum, Shoelace/Web Awesome, Material Web ou Carbon — le thème est une dépendance du composant, chargée une seule fois, jamais dupliquée dans chaque fichier de composant.
- Sans cette feuille, les custom properties sont simplement non définies (valeur initiale CSS de la propriété ciblée, souvent `transparent` ou `medium`). Ce n'est pas un filet de sécurité à coder en dur ; c'est un prérequis d'intégration à documenter/respecter.

**Exceptions légitimes à cette règle :**

- Les mots-clés système du mode `forced-colors` (`ButtonText`, `Highlight`, `CanvasText`, …) utilisés dans les media queries d'accessibilité. Ce ne sont pas des valeurs de marque et ils ne doivent jamais passer par les tokens — ils appartiennent au thème du système d'exploitation de l'utilisateur, pas au design system.
- `::backdrop` (`modal.css`) : avant Chrome 122, Firefox 120 et Safari 17.4 — tous dans la [matrice supportée](?path=/docs/documentation-support-navigateurs--docs) —, le pseudo-élément n'hérite de rien, ni de `:host` ni de `:root`. Aucun token ne peut l'atteindre, donc `var(--u-modal-backdrop-color, hsl(0deg 0% 0% / 50%))` porte un fallback littéral, aligné sur `--u-shadow-backdrop` (thème clair). Sur les navigateurs récents, le token s'applique normalement, dark mode compris.

### Accessibilité : `prefers-reduced-motion`

`tokens/motion.css` redéfinit `--u-motion-duration-*` à `0ms` sous `@media (prefers-reduced-motion: reduce)`. Comme chaque composant consomme `var(--u-motion-duration-fast)` plutôt qu'une durée codée en dur, toutes les transitions de tous les composants se désactivent simultanément via ce seul point de contrôle — un composant n'a donc jamais besoin de sa propre media query `prefers-reduced-motion`.

## Méthodologie

L'architecture suit plusieurs principes clés:

- **BEM (Block Element Modifier)**: Une convention de nommage pour créer des styles modulaires et réutilisables.
- **CSS Atomique**: Classes utilitaires pour les styles communs afin de promouvoir la réutilisabilité et réduire la spécificité.
- **Design Responsive**: Approche "mobile-first" avec des utilitaires responsives pour différentes tailles d'écran.

## Conclusion

Cette architecture CSS vise à créer un système de style évolutif et maintenable qui peut se développer avec le projet tout en assurant une apparence et une expérience cohérentes dans toute l'application.
