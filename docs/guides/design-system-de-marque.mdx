# Créer un design system de marque

Ce guide crée un design system de marque : un package qui dépend du socle, l'étend et le republie sous son propre préfixe. Les applications de la marque ne dépendent que de lui. Le modèle est décrit dans l'[ADR 0001](?path=/docs/documentation-adr-0001-architecture-multi-marque--docs).

L'exemple complet est `examples/acme-design-system`. Les extraits de ce guide en sont tirés, simplifiés.

## Prérequis

- Node 26 et npm 11.12, ou une version plus récente.
- Les archives du socle. Le socle n'est pas publié : à la racine du dépôt, lancez `npm run build`, puis `npm pack -w @unicorne/tokens -w @unicorne/icons -w @unicorne/components`.

## 1. Déclarez les dépendances

```json
{
  "dependencies": {
    "@unicorne/components": "file:../unicorne-components-0.0.0.tgz",
    "@unicorne/icons": "file:../unicorne-icons-0.0.0.tgz",
    "@unicorne/tokens": "file:../unicorne-tokens-0.0.0.tgz"
  },
  "devDependencies": {
    "@terrazzo/cli": "^2.10.0",
    "@terrazzo/token-tools": "^2.10.0",
    "svgo": "^4.1.0"
  },
  "peerDependencies": { "lit": "^3.3.3" }
}
```

- `@unicorne/tokens` contient les tokens et leur outillage. `@unicorne/components` contient les composants ([ADR 0003](?path=/docs/documentation-adr-0003-packages-tokens-et-composants--docs)). `@unicorne/icons` contient les icônes et leur générateur ([ADR 0005](?path=/docs/documentation-adr-0005-icônes--docs)).
- Lit est une peer dependency : l'application en fournit une seule copie.
- Terrazzo génère le CSS des tokens de la marque, avec le plugin du socle. SVGO optimise ses icônes, avec le générateur du socle.
- Dans `tsconfig.json`, activez `experimentalDecorators` et désactivez `useDefineForClassFields`, pour les décorateurs de Lit.
- Dans un fichier `.d.ts`, ajoutez les types des imports CSS : `/// <reference types="@unicorne/components/css-modules" />`.

## 2. Configurez le build

```ts
// vite.config.ts
import { cssImportAttributes } from "@unicorne/components/vite-plugin";

export default defineConfig({
  plugins: [cssImportAttributes()],
  build: {
    cssCodeSplit: true,
    lib: {
      entry: {
        index: "src/index.ts",
        define: "src/define.ts",
        styles: "src/styles.css",
        reset: "src/reset.css",
      },
      formats: ["es"],
    },
    rolldownOptions: { external: [/^lit/, /^@unicorne\//] },
  },
});
```

- `cssImportAttributes()` compile les imports `with { type: "css" }`.
- `external` garde Lit et le socle en dépendances : le build de la marque ne les copie pas.
- Lancez Terrazzo et le générateur d'icônes avant Vite : `"build": "tz build && unicorne-icons icons --out src/icons --export acmeIcons && vite build && …"`.

## 3. Écrivez les tokens de la marque

Les règles des tokens et du format DTCG sont dans [Tokens et couches CSS](?path=/docs/documentation-référence-tokens-et-couches-css--docs).

1. Écrivez vos palettes dans `tokens/primitive/palette.tokens.json`. Gardez les pas du socle, de 100 à 900.

   ```json
   {
     "palette": {
       "$type": "color",
       "brand": {
         "600": {
           "$value": {
             "colorSpace": "srgb",
             "components": [0.4771, 0.2917, 0.7303],
             "hex": "#7a4aba"
           }
         }
       }
     }
   }
   ```

   Le pas 600 porte un texte blanc, le pas 300 un texte presque noir. Les deux thèmes du socle en dépendent.

2. Changez un token sémantique seulement si la marque change une intention. ACME change la police du texte :

   ```json
   { "font": { "family": { "body": { "$value": "{font-family.serif}" } } } }
   ```

3. Rangez vos fichiers comme ceux du socle. La place d'un fichier donne son set ou son modifier :
   - `primitive/<nom>.tokens.json` : le set `primitive` ;
   - `semantic/<nom>.tokens.json` : le set `semantic` ;
   - `semantic/theme.dark.tokens.json` : le contexte `dark` du modifier `theme` ;
   - `component/<composant>/<composant>.tokens.json` : le set `component` ;
   - `component/<composant>/<attribut>.<valeur>.tokens.json` : le contexte `<valeur>` du modifier `<composant>-<attribut>`.

4. Configurez Terrazzo avec le plugin du socle :

   ```ts
   // terrazzo.config.ts
   import { defineConfig } from "@terrazzo/cli";
   import { brandResolver, tokensCss } from "@unicorne/tokens/terrazzo-plugin";

   export default defineConfig({
     tokens: [brandResolver({ name: "acme", sources: "./tokens" })],
     outDir: "./src/",
     plugins: [tokensCss({ brand: "acme", layer: "u.tokens.brand", page: "theme.css" })],
   });
   ```

   - `brandResolver()` écrit `tokens/.acme.resolver.json` : les sets et les modifiers du socle, puis vos fichiers. Vous ne listez aucun fichier du socle.
   - `brand: "acme"` place vos tokens sur `[data-brand="acme"]`, et limite la sortie à vos fichiers.
   - `layer: "u.tokens.brand"` place les tokens de la marque après ceux du socle.
   - Un modifier d'un composant de la marque se déclare dans `brandResolver()` : `modifiers: { "card-size": { default: "medium" } }`.

5. Ignorez `tokens/.*.resolver.json` et `src/theme.css` dans git : le build les écrit.

6. Lancez `npx tz build`. Le plugin écrit `src/theme.css`, ou échoue si un token enfreint la règle de son niveau.

7. Importez `theme.css` après `tokens.css`. Importé avant, `u.tokens.brand` passe sous `u.tokens.base`.

   ```css
   /* src/styles.css : la feuille que chargent les applications de la marque */
   @import "@unicorne/components/styles.css";
   @import "@unicorne/tokens/tokens.css";
   @import "./theme.css";
   ```

8. Publiez aussi `theme.css` seul, dans une entrée `./theme.css`. Une page d'un autre design system le charge pour une zone de votre marque.

9. Republiez le reset optionnel, pour que les applications ne dépendent que de la marque :

   ```css
   /* src/reset.css */
   @import "@unicorne/components/reset.css";
   ```

10. Vérifiez le contraste dans les deux thèmes, avec `contrastFailures()` :

```ts
import { contrastFailures } from "@unicorne/tokens/testing";

for (const theme of ["light", "dark"]) {
  document.documentElement.dataset.theme = theme;
  expect(contrastFailures()).toEqual([]);
}
```

Les paires mesurées et leurs minimums sont dans [Tokens et couches CSS](?path=/docs/documentation-référence-tokens-et-couches-css--docs).

- **Application de la marque :** elle pose `data-brand="acme"` sur `<html>`. Sans cet attribut, la page affiche le socle.
- **Zone de la marque dans une autre page :** la page charge votre `theme.css` et pose `data-brand="acme"` sur un conteneur. Vérifiez le contraste avec `contrastFailures(conteneur)`.
- **Thème d'une zone :** `data-theme="dark"` ou `data-theme="light"` sur un conteneur. Les règles sont dans [Tokens et couches CSS](?path=/docs/documentation-référence-tokens-et-couches-css--docs).
- **Composants propres à la marque :** ajoutez leurs paires à celles du socle : `contrastFailures(document.body, [...contrastPairs, { foreground, background, minimum }])`.

## 4. Étendez un composant du socle

1. Changez la valeur par défaut d'un token du composant dans `tokens/component/button/button.tokens.json` :

   ```json
   { "button": { "border-radius": { "$value": "{radius.full}" } } }
   ```

2. Donnez au plugin la feuille du groupe : `components: { button: { file: "components/acme-button/acme-button.tokens.css" } }`.
3. Étendez la classe, et adoptez la feuille générée après celles du socle :

   ```ts
   import { Button } from "@unicorne/components";
   import acmeButtonStyles from "./acme-button.css" with { type: "css" };
   import acmeButtonTokens from "./acme-button.tokens.css" with { type: "css" };

   /**
    * @element acme-button
    * @tokens button - The tokens ACME changes.
    */
   export class AcmeButton extends Button {
     static styles = [Button.styles ?? [], acmeButtonTokens, acmeButtonStyles];
   }
   ```

4. Stylez les éléments internes par leurs parts, dans la feuille de la classe :

   ```css
   /* acme-button.css */
   [part~="button"] {
     text-transform: uppercase;
   }
   ```

- Les classes internes du socle (`.button`) ne sont pas une API.
- Les tokens, parts, slots, événements et membres `protected` documentés sont l'API publique du socle. Le test de contrat du socle vérifie les parts.

## 5. Ajoutez un composant de marque

```ts
import { Button, DSBaseElement } from "@unicorne/components";
import { html } from "lit/static-html.js";

/**
 * @element acme-card
 * @tokens card - Its tokens.
 */
export class AcmeCard extends DSBaseElement {
  static override componentName = "card";
  static override dependencies = [Button];

  render() {
    const button = this.tagFor(Button);
    return html`<article><slot></slot><${button}>Action</${button}></article>`;
  }
}
```

- `componentName` donne la balise : `acme-card`.
- Déclarez dans `dependencies` chaque composant rendu, et obtenez sa balise avec `tagFor()`. La carte rend ainsi le bouton de la marque.
- N'écrivez jamais une balise en dur, et n'appelez pas `document.createElement` pour un composant.
- Écrivez ses tokens dans le groupe DTCG `card`, avec une `$description` chacun. Ce sont des alias de tokens sémantiques.
- Préfixez-les avec le nom de la marque : `components: { card: { file: "…/acme-card.tokens.css", prefix: "acme" } }` donne `--acme-card-padding`.
- Adoptez la feuille générée avant celle du composant, comme à l'étape 4.
- Choisissez un nom absent du catalogue du socle. Si le catalogue contient un composant de même nom que `AcmeCard` ne l'étend pas, `defineComponents()` lève une erreur. Vérifiez le catalogue à chaque mise à jour du socle.

## 6. Remplacez et ajoutez des icônes

Les règles des fichiers SVG sont dans [Icônes](?path=/docs/documentation-référence-icônes--docs).

1. Écrivez vos icônes dans `icons/`, un fichier `<nom>.svg` par icône, sur une grille de 24 × 24.
2. Pour remplacer une icône du socle, donnez au fichier le nom de cette icône : `icons/information.svg`.
3. Lancez `npx unicorne-icons icons --out src/icons --export acmeIcons`. La commande écrit `src/icons/`, ou liste les fichiers refusés.
4. Ignorez `src/icons/` dans git : le build le génère.
5. Passez-les à votre design system, à l'étape 7 : `icons: acmeIcons`.

- Vos icônes passent par-dessus celles du socle, nom par nom.
- Chaque composant de l'enregistrement rend vos icônes : `acme-alert` rend `acme-icon`, avec votre `information`.
- Vite découpe chaque icône en un chunk de votre `dist/`. Une application télécharge seulement les icônes qu'elle affiche.
- Une icône du socle que vous ne remplacez pas reste dans `@unicorne/icons`, et se charge depuis ce package.

## 7. Déclarez le design system et republiez

```ts
// src/design-system.ts : n'enregistre rien, n'importe aucun composant
import { designSystem } from "@unicorne/components";
import { acmeIcons } from "./icons/index.js";

export const acme = designSystem({
  prefix: "acme",
  catalog: ["button", "alert", "modal", "icon", "text-field", "textarea", "autocomplete", "card"],
  overrides: {
    button: () =>
      import("./components/acme-button/acme-button.js").then((module) => module.AcmeButton),
  },
  icons: acmeIcons,
  labels: { closeLabel: "Fermer", errorLabel: "Erreur :" },
  version: __ACME_VERSION__,
});
```

- `designSystem({ prefix: "acme" })` seul propose tout le socle, sans surcharge.
- `labels` donne la valeur par défaut d'une propriété, par nom, à chaque composant qui a cette propriété : les textes de la langue de la marque. Un attribut de l'élément l'emporte.
- `version` est la version du package de la marque. Votre build la remplace : `define: { __ACME_VERSION__: … }` dans `vite.config.ts`.
- `catalog` liste les composants qu'une application peut demander. ACME ne propose pas `button-link`. Sans `catalog`, une application peut demander tout composant.
- Un composant s'enregistre avec les composants qu'il rend, listés ou non : `acme-card` enregistre `acme-button`.
- `overrides` remplace un composant dans tout l'enregistrement : `acme-modal` et `acme-card` rendent `AcmeButton`.
- Une surcharge donnée par `import()` se télécharge avec le premier composant enregistré qui la rend.

```ts
// src/define.ts : tout le catalogue, pour une application qui utilise tout
import {
  Alert,
  Autocomplete,
  Button,
  Icon,
  Modal,
  Textarea,
  TextField,
} from "@unicorne/components";
import { AcmeCard } from "./components/acme-card/acme-card.js";
import { acme } from "./design-system.js";

void acme.define(Button, Alert, Modal, Icon, TextField, Textarea, Autocomplete, AcmeCard);
```

```ts
// src/index.ts : le socle, republié avec le design system de la marque
export * from "@unicorne/components";
export type { AcmeButton } from "./components/acme-button/acme-button.js";
export * from "./components/acme-card/acme-card.js";
export type { AcmeCatalog } from "./catalog.js";
export { acme } from "./design-system.js";
```

```ts
// src/catalog.ts : le catalogue de la marque, en types
import type { Catalog } from "@unicorne/components";

export interface AcmeCatalog extends Omit<Catalog, "button" | "button-link"> {
  button: { element: AcmeButton; events: {} };
  card: { element: AcmeCard; events: {} };
}

// src/define.ts : les types de `document.querySelector("acme-button")`
declare global {
  interface HTMLElementTagNameMap extends TagNameMap<"acme", AcmeCatalog> {}
}

// src/vue.ts : une entrée de types, pour les applications Vue
declare module "vue" {
  interface GlobalComponents extends VueElements<"acme", AcmeCatalog> {}
}
```

- `AcmeCatalog` décrit chaque balise une fois : son élément et ses événements. Les types des balises en dérivent.
- Publiez `src/vue.ts` dans une entrée `./vue`, de types seulement : `"./vue": { "types": "./dist/vue.d.ts" }`. `VueElements` vient de `@unicorne/components/vue`.
- N'exportez pas depuis `index.ts` la classe d'une surcharge chargée par `import()` : `index.js` la contiendrait. Publiez-la dans sa propre entrée, comme `./acme-button`.
- Déclarez `"sideEffects": ["**/*.css", "./dist/define.js"]` dans `package.json`. Le bundler d'une application retire alors les modules qu'elle n'importe pas.
- Partagez une seule copie de la marque entre les applications d'une page. Un second enregistrement garde les balises déjà définies. Son avertissement cite les versions des deux copies.
- Une application qui ne peut pas partager sa copie l'enregistre sous son propre préfixe : `acme.withPrefix("acme2").define(Alert)`. Ses balises sont `acme2-alert`, et son thème reste `[data-brand="acme"]`.

Une application enregistre ce qu'elle utilise :

```ts
import { acme, Alert } from "@acme/design-system";

await acme.define(Alert); // acme-alert et acme-icon, sans le bouton d'ACME
```

- `define()` se résout quand chaque balise est définie. Pendant le chargement, l'application stylise `:not(:defined)`.
- Une application qui utilise tout le catalogue importe `@acme/design-system/define`.
- Les règles de `define()` sont dans sa JSDoc, et ses raisons dans l'[ADR 0006](?path=/docs/documentation-adr-0006-design-system-de-marque--docs).
- Une application Vue suit le guide [Utiliser une marque dans une application Vue](?path=/docs/documentation-guides-utiliser-une-marque-dans-une-application-vue--docs).

## 8. Générez le manifest

```js
// custom-elements-manifest.config.mjs
import { tokensManifest } from "@unicorne/components/cem-plugin";
import { brandResolver } from "@unicorne/tokens/dtcg-sources";

export default {
  globs: ["src/**/*.ts"],
  exclude: ["src/define.ts", "src/**/*.d.ts"],
  outdir: ".",
  litelement: true,
  dependencies: true,
  plugins: [
    tokensManifest({
      resolver: brandResolver({ name: "acme", sources: "tokens" }),
      components: { card: { prefix: "acme" } },
      emit: (file) => !file.includes("/node_modules/"),
    }),
  ],
};
```

- `dependencies: true` inclut le manifest du socle. Un composant qui étend le socle est documenté avec ce qu'il hérite : attributs, tokens, parts.
- `tokensManifest()` documente les tokens de chaque classe qui porte `@tokens`, depuis les sources DTCG de la marque.
- L'analyseur affiche `Cannot resolve './x.js'` pour les sources TypeScript. Ce message est sans effet.

## 9. Vérifiez

À la racine du dépôt du socle, lancez `npm run example`. La commande empaquette les trois packages du socle, puis installe, construit et teste ACME. Le test vérifie que :

- le `dist/` d'ACME importe `@unicorne/components` au lieu de le copier ;
- `dist/theme.css` contient les seules valeurs d'ACME, sur `[data-brand="acme"]` ;
- dans une page du socle, une zone ACME affiche les valeurs d'ACME, et le reste de la page celles du socle ;
- une zone sombre d'une page claire est sombre et garde un contraste AA, et une zone claire d'une page sombre est claire ;
- une zone ACME dans une zone sombre affiche le pas sombre de la palette d'ACME ;
- les tokens d'ACME atteignent les composants du socle, et gardent un contraste AA dans les deux thèmes ;
- les styles d'`AcmeButton` s'ajoutent à ceux du socle ;
- la carte d'ACME lit ses tokens `--acme-card-*` ;
- la modale et la carte d'ACME rendent `AcmeButton` ;
- l'alerte d'ACME rend l'icône `information` d'ACME, et `acme-icon` rend l'icône `star` d'ACME ;
- `acme-text-field` reçoit le thème d'ACME, soumet sa valeur avec son formulaire et la valide ;
- `acme-textarea` reçoit le thème d'ACME et soumet sa valeur avec son formulaire ;
- `acme-autocomplete` propose ses enfants `<option>`, dans le thème d'ACME, et soumet la suggestion choisie ;
- ACME ne propose pas `button-link` : `acme.define(ButtonLink)` est rejeté ;
- une application qui enregistre seulement `Alert` définit `acme-alert` et `acme-icon`, et ne télécharge pas le bouton d'ACME ;
- le `dist/` d'ACME contient ses icônes en chunks séparés, et aucune icône du socle ;
- la page télécharge seulement les icônes du socle qu'elle affiche ;
- la page ne télécharge pas Floating UI, car Chromium ancre les popovers en CSS ;
- aucune balise `u-` n'est enregistrée ;
- le manifest d'ACME documente ce qu'`AcmeButton` hérite du socle.

Une marque dont une application rend ses pages sur un serveur suit le guide [Rendre une marque sur un serveur](?path=/docs/documentation-guides-rendre-une-marque-sur-un-serveur--docs).

La commande empaquette ensuite ACME, puis installe, construit et teste l'application Vue `examples/acme-vue-app` ([Utiliser une marque dans une application Vue](?path=/docs/documentation-guides-utiliser-une-marque-dans-une-application-vue--docs)).
