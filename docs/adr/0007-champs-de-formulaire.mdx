# ADR 0007 — Champs de formulaire

**Statut :** accepté · **Date :** 14 novembre 2026

## Contexte

`text-field` rend dans son shadow root un libellé, un indice, un `<input>` natif et un message d'erreur. Il porte aussi le comportement dans le formulaire : valeur, validité, reset, `<fieldset disabled>`.

Chaque type de champ a besoin du même libellé, du même indice et de la même erreur : zone de texte, liste, case à cocher. Recopier ce code dans chaque composant le multiplie.

Une piste est un composant `form-field` : il porte le libellé et l'indice, et reçoit le contrôle dans un slot.

### La contrainte : les références entre shadow roots

- Un `<label for>` nomme l'élément qui porte cet `id` « in the tree » : l'arbre du libellé (HTML). Un `aria-labelledby` ou un `aria-describedby` cherche aussi son `id` dans son propre arbre.
- `ariaLabelledByElements` et `ariaDescribedByElements` prennent des éléments, pas des `id`. Le navigateur garde un élément seulement s'il est « a descendant of any of element's shadow-including ancestors » (HTML).
- Un contrôle dans un shadow root peut donc viser le light DOM, mais pas le shadow root d'un composant voisin.
- Au 14 novembre 2026, ces propriétés existent depuis Chrome et Edge 135, Firefox 136 et Safari 16.4.
- Reference Target redirige un `id` du light DOM vers un élément d'un shadow root. Il « only works for ID references pointing into a shadow tree ».
- Au 14 novembre 2026, seuls Chrome et Edge 152 livrent Reference Target. Firefox et Safari ne le livrent pas.
- La [matrice](?path=/docs/documentation-référence-support-navigateurs--docs) exige Chrome 111, Firefox 115 et Safari 16.4.
- Aucun polyfill ne crée de relation dans l'arbre d'accessibilité : le navigateur le construit seul, avec ces mécanismes.
- Les contournements recopient le libellé dans un `aria-label` du contrôle. Le libellé visible et le nom accessible sont alors deux textes séparés. Un clic sur le libellé ne donne pas le focus au contrôle.

### Critères de décision

1. Le libellé, l'indice et l'erreur sont accessibles dans toute la matrice : nom accessible, description, clic sur le libellé.
2. Un type de champ reprend le libellé, l'indice, l'erreur et le comportement dans le formulaire sans les recopier.
3. Une application écrit un champ sans relier d'`id` à la main.
4. Un composant ne modifie pas les enfants que le framework de l'application gère (Vue, React).

## D1 — Où vivent le libellé, l'indice et l'erreur

- **Option A — `form-field` avec le libellé dans son shadow root et le contrôle dans un slot :** `<u-form-field label="Nom"><u-input></u-input></u-form-field>`.
  - Le libellé et l'`<input>` sont dans deux shadow roots voisins.
  - Ni un `id`, ni `ariaLabelledByElements`, ni Reference Target ne les relient : le critère 1 échoue.
- **Option B — `form-field` avec un contrôle natif dans le light DOM :** `<u-form-field label="Nom"><input name="name"></u-form-field>`.
  - Le formulaire natif fonctionne sans `ElementInternals`.
  - Le `form-field` crée le libellé, l'indice et l'erreur dans le light DOM, avec leurs `id` : le critère 4 échoue.
  - Ses styles atteignent le contrôle seulement par `::slotted()`.
- **Option C — `form-field` avec un libellé écrit par l'application dans le light DOM :** `<label slot="label" for="name">`.
  - Il fonctionne dans toute la matrice.
  - L'application relie chaque `id` à la main : le critère 3 échoue.
- **Option D — Une classe de base abstraite `FieldBase` :**
  - Chaque champ rend son libellé, son indice, son contrôle natif et son erreur dans son propre shadow root.
  - La base porte ce code une seule fois.
  - C'est la convention du socle pour une famille de composants, comme `ButtonBase`.

**Décision : D.**

```ts
export abstract class FieldBase extends withInternals(withDisabled(DSBaseElement)) {
  // label, hint, value, required, error-message, error-label, validité, formulaire
  protected abstract renderControl(): unknown;
}

export class Textarea extends FieldBase {
  static override componentName = "textarea";

  protected renderControl() {
    return html`<textarea part="textarea" class="control" id="control" …></textarea>`;
  }
}
```

- `FieldBase` rend, dans cet ordre :
  - le libellé, avec `for="control"` ;
  - l'indice ;
  - le contrôle ;
  - l'erreur.
- Un champ écrit seulement `renderControl()` et ses contraintes : `type` et `pattern` pour `text-field`, `rows` pour `textarea`.
- Les tokens `--u-field-*` sont communs à tous les champs.
- Le contrat de `renderControl()` est dans la JSDoc de `packages/components/src/bases/field/field-base.ts`.

## Conséquences

- **Code :** `FieldBase`, `text-field` et `textarea`, dans `packages/components/src/components/`. ACME propose les deux champs.
- **Tokens :** le groupe `field`, commun aux champs.
- **Tests :** les stories des deux champs, le test d'ACME et celui de l'application Vue `examples/acme-vue-app`.
- **Limites :**
  - Le libellé et l'indice sont du texte : la propriété `label` ne porte ni lien ni mise en forme.
  - Un champ ne reçoit pas de contrôle de l'application : chaque contrôle est un composant qui étend `FieldBase`.
  - L'ordre du rendu convient aux contrôles de texte. Une case à cocher a son libellé après le contrôle. Un groupe d'options demande un `<fieldset>` et sa `<legend>`. Ces composants surchargent `render()` ou ont leur propre base.
- **Documentation :** cet ADR, le skill `lit-component` et `AGENTS.md`.

## Questions ouvertes

- **Reference Target dans toute la matrice :** un `<label for>` du light DOM nomme alors le contrôle d'un composant. Un contrôle sans libellé, que l'application nomme comme un `<input>` natif, devient possible. Il complète `FieldBase` sans le remplacer.
- **Libellé enrichi :** un libellé avec un lien ou une mise en forme demande un slot `label` dans le shadow root du champ. Son nom accessible est à vérifier dans les trois moteurs.
