# Architecture CSS

Cette page explique pourquoi les styles du socle sont organisés ainsi. Les règles elles-mêmes sont dans [Tokens et couches CSS](?path=/docs/documentation-référence-tokens-et-couches-css--docs).

## Des couches, toutes sous `u`

Les couches de cascade rendent la priorité explicite. Un style de la couche `u.utilities` l'emporte sur un style de `u.base`, quelle que soit sa spécificité.

Les noms de couches sont globaux au document. Des noms nus fusionneraient avec les couches de l'application. Tailwind CSS v4, par exemple, déclare `theme, base, components, utilities`. Le préfixe `u` évite cette collision, comme le préfixe `--u-` des tokens ([ADR 0001](?path=/docs/documentation-adr-0001-architecture-multi-marque--docs), D4).

L'application garde la main : ses styles hors couche l'emportent sur toutes les couches du socle.

## Les sous-couches des tokens sont ordonnées par leurs blocs

Les tokens d'une marque doivent l'emporter sur ceux du socle. Ils vivent dans `u.tokens.brand`, après `u.tokens.base`.

Une déclaration `@layer u.tokens.base, u.tokens.brand;` fixerait cet ordre quel que soit l'ordre d'import. Elle ne survit pas aux outils de build :

- Lightning CSS, le minifieur de Vite, la découpe. `u.tokens.brand` n'a pas de bloc dans le socle : il devient un `@layer u.tokens.brand;` isolé, après le bloc de `u.tokens.base`.
- postcss-import, qui résout les `@import` dans Vite, remonte en tête de fichier les `@layer` sans bloc qui suivent d'autres at-rules.
- Quand une marque ou une application bundle la feuille des tokens du socle, `u.tokens.brand` passe donc avant `u.tokens.base`, et la marque perd.

Sans cette déclaration, l'ordre des sous-couches est celui de leurs blocs. La marque importe sa feuille après `tokens.css`, et aucun outil ne déplace un bloc.

## Trois niveaux de tokens

Un changement de marque ou de thème doit toucher un seul niveau.

- **Les primitives** portent les valeurs brutes, les mêmes dans les deux thèmes. Une marque change surtout elles : ses palettes, ses polices.
- **Les tokens sémantiques** nomment une intention : `action`, `danger`. Ils choisissent une primitive par thème. Sans eux, chaque composant lirait une primitive, et le thème sombre se répéterait dans chaque composant.
- **Les tokens de composant** donnent à l'application et aux marques un réglage par composant, sans toucher aux autres.

## Les thèmes vivent dans les tokens sémantiques

Une palette est une échelle de clarté : le pas 600 est sombre, le pas 300 est clair, quelle que soit la teinte. Le thème clair met les fonds d'intention au pas 600 sous un texte blanc. Le thème sombre les met au pas 300 sous un texte presque noir.

Une marque fournit donc ses palettes avec les mêmes pas. Elle hérite des deux thèmes du socle, sans écrire de valeur sombre. Son contraste reste celui du socle, à la teinte près. `contrastFailures()` le vérifie.

Material 3 et Primer suivent ce modèle : des palettes de référence communes aux thèmes, et des rôles sémantiques qui changent avec le thème.

## Le survol et l'appui sont des pas de palette

Le survol prend le pas suivant, à l'opposé du texte : 700 en clair, 200 en sombre. L'appui prend le pas d'après. Le fond s'éloigne du texte, et le contraste ne peut qu'augmenter.

Un mélange calculé (`color-mix()`) donnerait le même effet avec une seule couleur par intention. Mais ni le format DTCG ni les variables Figma ne savent l'exprimer. Les pas de palette s'écrivent dans les deux.

## Les sources sont en DTCG, le CSS est généré

Les tokens des marques viennent de Figma (ADR 0001). Le format DTCG est le format d'échange des outils de design : Figma, Tokens Studio, Terrazzo et Style Dictionary le lisent ou l'écrivent. Les sources du socle sont donc en DTCG, et le CSS en est généré.

Le CSS généré est commité, comme `custom-elements.json`. Une revue voit chaque changement de valeur. `npm run tokens:check` garantit qu'il correspond aux sources.

Les variantes d'un composant sont des modifiers du resolver, comme le thème. Figma les représente de la même façon : des modes d'une collection de variables.

Le plugin vérifie les trois niveaux à chaque build. Une règle écrite dans une page seulement ne tiendrait pas face à un export Figma.

## Les variantes changent les tokens sur l'hôte

Une déclaration posée sur l'hôte depuis la page l'emporte sur une règle `:host(…)` de la feuille du composant. Une variante qui change ses tokens dans `:host([variant="danger"])` laisse donc gagner la valeur de l'application.

Un token redéclaré sur un élément interne écraserait au contraire la valeur héritée de l'hôte. L'application perdrait son réglage, pour cette variante seulement.

## Pas de valeur de repli littérale

Une valeur de repli (`var(--u-color-action-background, #1c65c8)`) recopie une valeur qui existe déjà dans les primitives. Avec deux composants, deux copies divergent sans bruit.

La feuille de tokens est donc une dépendance des composants, chargée une fois par l'application. Spectrum, Web Awesome, Material Web et Carbon suivent la même convention.

`::backdrop` est l'exception : avant Chrome 122, Firefox 120 et Safari 17.4, aucun token ne l'atteint.

## Les tokens du socle sont déclarés sur `:root` et sur `[data-brand]`

Un `var()` est résolu sur l'élément qui déclare la custom property. L'élément enfant hérite de la valeur résolue.

Déclarés sur `:root` seulement, les tokens sémantiques garderaient les primitives de `:root`. Un conteneur qui redéfinit les primitives n'aurait aucun effet sur les composants. Déclarés aussi sur `[data-brand]`, ils suivent les primitives de ce conteneur.

Les primitives du socle sont déclarées sur `[data-brand]` pour une autre raison. Une marque invitée dans la page d'une autre marque hériterait sinon des palettes de la marque hôte. Chaque conteneur de marque repart donc des valeurs du socle ([ADR 0013](?path=/docs/documentation-adr-0013-portées-de-marque-et-de-thème--docs), D2).

## Le thème d'une marque vise toujours `[data-brand]`

Une marque est tantôt celle de la page, tantôt celle d'une zone : sa carte produit dans la page d'un autre design system. Une feuille qui vise `:root` ne sert que le premier cas.

La feuille d'une marque vise donc `[data-brand="<marque>"]`. L'application de la marque pose l'attribut sur `<html>`. Une page d'un autre design system le pose sur un conteneur. La même feuille sert les deux cas.

## Un thème s'applique à une zone

Une navigation sombre au-dessus d'un contenu clair est un besoin courant. Le thème n'est donc pas réservé à `<html>` : tout élément qui porte `data-theme` redéclare les couleurs sémantiques de son thème.

Un conteneur de marque redéclare aussi ces couleurs, avec ses palettes. Il doit donc connaître son thème. Les sélecteurs lui donnent celui de la zone la plus proche, sur deux niveaux. `light-dark()` lèverait cette limite : il est absent avant Chrome 123 et Safari 17.5.

## Une feuille CSS par composant

Un fichier `.css` voisin reste du CSS : `doiuse` l'analyse, et il se lit sans connaître Lit. Importé comme CSS module script, il donne à Lit une feuille constructible, partagée par toutes les instances.

Le standard donnerait un `CSSStyleSheet`. Node n'en a pas : le socle ne s'importerait pas sur un serveur. Le plugin compile donc l'import en `CSSResult` de Lit, que Lit adopte dans le navigateur et rend en texte sur un serveur ([ADR 0014](?path=/docs/documentation-adr-0014-vue-et-rendu-serveur--docs)).

Les navigateurs de la matrice ne savent pas tous importer un CSS module script. Le plugin `packages/components/plugins/css-import-attributes.ts` compile donc l'import dans le JS livré. L'application et les marques n'ont rien à configurer.

## Un seul point de contrôle pour le mouvement

Les composants lisent leurs durées dans des tokens, qui pointent vers `motion.duration.*`. Le contexte `motion: reduced` met ces durées à zéro quand l'utilisateur demande moins de mouvement. Aucun composant n'a besoin de sa propre media query.
