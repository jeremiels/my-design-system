- Les styles de l'application hors couche l'emportent sur toutes les couches du socle.
- Les styles internes des composants vivent dans leur shadow DOM. Les couches de la page ne les atteignent pas.

- `order.css` ne déclare pas ces deux sous-couches. La raison est dans [Architecture CSS](?path=/docs/documentation-explication-architecture-css--docs).

## Sources DTCG

- Un token a un identifiant : son chemin dans les groupes, `color.action.background`.
- Son nom CSS est `--u-` suivi de l'identifiant, avec des tirets à la place des points : `--u-color-action-background`.
- Un alias s'écrit `{palette.brand.600}`. Il devient `var(--u-palette-brand-600)`.
- Une couleur est un objet `srgb` avec `components` et `hex`, la forme qu'exporte Figma.

Le plugin de génération fait échouer le build quand une de ces règles n'est pas respectée :

- Seules les primitives contiennent des valeurs littérales. Une primitive ne référence que des primitives.
- Un token sémantique est un alias de primitive ou de token sémantique.
- Un token de composant est un alias de token sémantique, avec une `$description`.
- Un token reste à un seul niveau.
- Un contexte change seulement des tokens qui ont une valeur par défaut.
- Les thèmes `light` et `dark` déclarent les mêmes tokens.
- Deux identifiants ne donnent jamais le même nom CSS.

## Génération

`npm run tokens` lance Terrazzo dans chaque package, sur le même resolver. Les deux builds utilisent le plugin `packages/tokens/plugins/terrazzo-plugin.ts`, exporté en `@unicorne/tokens/terrazzo-plugin`.

- `packages/tokens/terrazzo.config.ts` génère la feuille de page.
- `packages/components/terrazzo.config.ts` génère les feuilles des composants. Il associe chaque modifier de composant à un attribut de l'hôte.

- `tokens.css` est dans la couche `u.tokens.base`. Les feuilles des composants n'ont pas de couche.
- Les fichiers générés sont commités. N'éditez pas un fichier généré : changez la source DTCG, puis lancez `npm run tokens`.
- `npm run tokens:check` régénère les fichiers et échoue s'ils diffèrent de l'index git. `npm run check` le lance.
- `npm run build`, `npm run storybook` et `npm run build-storybook` lancent `npm run tokens`.

## Tokens de composant

- Les tokens d'un composant forment le groupe DTCG qui porte son nom : `button`, pour `u-button` comme pour `acme-button`.
- Ils vivent dans `@unicorne/tokens`, comme les autres niveaux : les implémentations natives les lisent aussi.
- Nom : `<composant>.<propriété-css>[-<état>]`, par exemple `button.background-color-hover`.
  - `<propriété-css>` est le nom complet de la propriété : `background-color`, pas `bg`.
- Chaque token a une `$description`. Elle documente le composant.
- Un modifier par attribut reflété : `<composant>-<attribut>`, par exemple `button-variant`. Chaque contexte change les valeurs par défaut sur l'hôte : `:host([variant="danger"])`.
- La classe nomme son groupe dans sa JSDoc : `@tokens button`. Le plugin `packages/components/plugins/cem-plugin.ts`, exporté en `@unicorne/components/cem-plugin`, ajoute ses tokens au manifest, avec leur valeur par défaut et leur description.
- La classe adopte la feuille générée avant sa propre feuille, comme dans la section Feuille d'un composant.
- Aucune règle d'un élément interne ne redéclare un token documenté.
- Les règles internes lisent les tokens du composant : `background-color: var(--u-button-background-color)`.

`packages/components/src/api-contract.test.ts` vérifie ces règles. Les tokens documentés sont exactement ceux déclarés sur `:host`. Aucun n'est redéclaré ailleurs. Un token posé sur l'hôte s'applique dans chaque état `:host([…])`.

## Valeurs de repli

Un `var()` n'a pas de valeur de repli littérale : la feuille de tokens est une dépendance des composants. Deux exceptions :

- Les mots-clés système de `forced-colors` (`ButtonText`, `Highlight`, `CanvasText`) dans les media queries d'accessibilité.
- `::backdrop` dans `modal.css` : avant Chrome 122, Firefox 120 et Safari 17.4, il n'hérite d'aucune custom property. Sa valeur de repli recopie `color.backdrop` du thème clair.

- Un thème change les tokens sémantiques de couleur. Les primitives sont les mêmes dans les deux thèmes.
- La feuille de page déclare aussi `color-scheme`, avec les mêmes déclencheurs : `light dark` sur `:root`, puis `light` ou `dark` selon `data-theme`.
- `color-scheme` donne le thème à l'interface du navigateur : canevas, barres de défilement, champs natifs.
- L'application ajoute `<meta name="color-scheme" content="light dark">` à son `<head>`. Le navigateur connaît les thèmes avant de charger les feuilles.
- Une marque change ses palettes et garde les deux thèmes du socle. Elle n'écrit aucune valeur sombre, et sa feuille ne déclare pas `color-scheme`.
- Un composant ne contient aucune logique de thème.

## Mouvement réduit

Le contexte `motion: reduced` met `motion.duration.*` à `{duration.0}` sous `@media (prefers-reduced-motion: reduce)`. Les composants lisent ces tokens et n'ont pas leur propre media query.

## Feuille d'un composant

Les styles d'un composant ou d'un mixin vivent dans un fichier `.css` voisin, importé comme CSS module script. Un composant adopte aussi la feuille de ses tokens :

```ts
import alertStyles from "./alert.css" with { type: "css" };
import alertTokens from "./alert.tokens.css" with { type: "css" };

static styles = [DSBaseElement.styles ?? [], alertTokens, alertStyles];
```

- L'import donne un `CSSStyleSheet` constructible, que Lit adopte.
- Le plugin `packages/components/plugins/css-import-attributes.ts` compile cet import pour Vite, Storybook, Vitest et le build.
- Les classes internes (`.button`) ne sont pas une API. Une marque style les éléments internes par leurs parts : `[part~="button"]`.
