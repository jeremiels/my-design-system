# Copilot Instructions for My Design System

## Project Overview

- **Purpose:** TypeScript design system on [Lit](https://lit.dev/) providing reusable web components (e.g., `u-button`, `u-modal`).
- **Build:** [Vite](https://vitejs.dev/) (v8 beta) bundles to ES modules; Lit is external (consumers install separately).
- **Testing:** [Vitest](https://vitest.dev/) with Storybook integration; stories run in Chromium, Firefox and WebKit via Playwright, plus a real Firefox ESR smoke test of `dist/`.
- **Linting:** [Oxlint](https://oxlint.com/) for TypeScript with `oxfmt` for formatting.
- **Node:** v24.8.0+; npm v11.6.0+

## Key Directories & Files

- `src/index.ts` — Main entry point; exports all public components (ES modules only).
- `src/components/` — Web components live here; each component gets its own folder (e.g., `button/`, `modal/`). Each component folder includes:
  - `component-name.ts` — The main component class
  - `component-name.css` — Its shadow-DOM styles, imported as a `CSSStyleSheet` (see Component Styles below)
  - `component-name.type.ts` — Types local to that component
  - `component-name.stories.ts` — Storybook stories and visual tests
  - Variant files (e.g., `button-link.ts` + `button-link.css`) for extended behaviors
- `src/mixins/` — Reusable behavior mixins (e.g., `withDisabled.ts`, `withInternals.ts`) that compose with components; a mixin with styles keeps them in a sibling `.css` file (`withDisabled.css`).
- `plugins/css-import-attributes.ts` — Local Vite plugin implementing `import sheet from "./x.css" with { type: "css" }` (Vite has no native support); unit-tested in `css-import-attributes.test.ts`.
- `scripts/` — `check-css-compat.mjs` (doiuse against browserslist) and `install-firefox-esr.sh` (downloads the Firefox ESR used by `test:legacy`).
- `tests/legacy/` — Smoke test of the built `dist/` in a real Firefox ESR (`run.mjs` drives `index.html` + `checks.js` through WebdriverIO).
- `src/docs/adr/` — Architecture Decision Records. **ADR 0001 (accepted) sets the multi-brand target**: classes without self-registration + `defineComponents({ prefix, overrides })`, declared inter-component dependencies (no hard-coded tags), documented extension surface, `--u-` prefix on every token, generated Custom Elements Manifest, Lit as a peer dependency. The migration is complete: the conventions below follow it.
- `src/registry/` — `define-components.ts` (`defineComponents({ prefix, components, overrides })`, registers each component as `<prefix>-<componentName>`) and `catalog.ts` (`allComponents`).
- `src/define.ts` — Side-effect entry (`my-design-system/define`) registering the catalog under the default `u-` prefix, for Storybook, the demo and brand-less apps; also holds the `u-*` `HTMLElementTagNameMap` declarations. `src/index.ts` itself is side-effect free.
- `custom-elements.json` — Custom Elements Manifest (ADR 0001, D5), generated by `npm run analyze` from the JSDoc (config: `custom-elements-manifest.config.mjs`), **committed** so API changes show in review, published with the package, and fed to Storybook autodocs and controls.
- `examples/acme-design-system/` — Example brand design system (ADR 0001): consumes the base through `npm pack`, sets a theme (`tokens.brand`), extends `Button`, adds `AcmeCard`, registers the `acme-` prefix and republishes. `npm run example` (`scripts/run-example.mjs`) builds the base, packs it, then installs, builds and smoke-tests the example — run it after any change to the package surface. Walkthrough: `src/docs/guides/design-system-de-marque.mdx`.
- `src/events/` — Custom event classes for the whole design system, one file per event, named `{owner}-{event}.ts` (e.g., `button-click.ts` → `ClickEvent`). Centralized regardless of how many components currently dispatch a given event — an event's name/shape is public API the moment it exists (it augments the global `GlobalEventHandlersEventMap`), unlike a private type, so this is the one place to scan "what does this design system emit" as it grows.
- `src/types/` — Shared types like `ComponentSize`, `SemanticVariant`, `ButtonVariant` (from `common.ts`).
- `src/components/base-element.ts` — Minimal base class with shadow DOM defaults (`box-sizing`, `[hidden]`), `dir`/`lang` reactive properties and the registration contract (`componentName`, `dependencies`, `tagFor()`).
- `src/styles/` — CSS organized by layer:
  - `main.css` — Entry point; imports and declares layer order
  - `layers/reset.css` — CSS reset for baseline consistency
  - `layers/tokens.css` — Token imports; organizes subdirectories
  - `layers/base.css` — Global element styles
  - `layers/utilities.css` — Utility classes (e.g., `.visually-hidden`)
  - `layers/shame.css` — Emergency overrides (must be documented with reason/ticket)
  - `tokens/` — Token files (color, spacing, typography) each declare `@layer tokens.{name}`
- `.storybook/` — Storybook config, setup files, and vitest integration

## Component Patterns

- **Base Class:** Extend `DSBaseElement` (`src/components/base-element.ts`) which provides shadow DOM defaults and inherits from `LitElement`.
- **Mixins:** Compose behaviors using mixins like `withDisabled()`. A mixin extends `Base` directly (real class composition, not a style-only merge) and adds properties/methods on top of it. Mixin signature:
  ```ts
  export function withDisabled<T extends Constructor<LitElement>>(Base: T);
  ```
  Call it with the base you want composed in — e.g. `withDisabled(DSBaseElement)` for the standard shadow-DOM defaults. `Base`'s own `static styles` are picked up automatically and merged with the mixin's own styles.
- **Properties & Types:** Use `@property()` decorator and types from `src/types/common.ts`:
  - `ComponentSize = "small" | "medium" | "large"`
  - `SemanticVariant = "success" | "danger" | "warning" | "information"` — Shared across components for semantic meaning
  - `ButtonVariant = "primary" | "secondary" | SemanticVariant` — Button-specific variants extending semantic variants
- **Custom Elements (ADR 0001, D1–D2):** a component class never registers itself — no `@customElement`, no `customElements.define`. It sets `static componentName = "button"` (tag name without prefix) and is added to `allComponents` in `src/registry/catalog.ts` and to the `HTMLElementTagNameMap` block of `src/define.ts`. `defineComponents()` registers a fresh subclass per prefix.
- **Public API (ADR 0001, D3/D5):** documented in the class JSDoc — `@element my-<name>`, `@summary`, `@slot`, `@csspart` (with a matching `part="…"` in the template), `@cssprop [--u-<component>-<prop>=<default>] - description` for every token declared on `:host`, `@fires`. Anything brands shouldn't rely on is `#private`/`private` or tagged `@internal`; documented `protected` members are public API for subclasses. Document shared API once on the base class (e.g. `ButtonBase`), and apply mixins inline (`extends withDisabled(DSBaseElement)`, not through a constant) so the analyzer follows inheritance. After any API change, run `npm run analyze` and commit `custom-elements.json`; `src/api-contract.test.ts` checks the manifest against the rendered components, and `npm run api:check` fails on a stale manifest.
- **Component Dependencies:** a component that renders another one lists its class in `static dependencies = [Button]` and renders it with `lit/static-html.js`: `const button = this.tagFor(Button); html\`<${button}>…</${button}>\``. Never hard-code another component's tag, nor create one with `document.createElement`: a brand's override (`overrides: { button: AcmeButton }`) would be bypassed. Any new `lit/...`import goes in`optimizeDeps.include` (`vite.config.ts`).
- **Accessibility:** Mixins like `withDisabled` manage aria attributes (e.g., `aria-disabled`). Use shadow DOM `:host` selectors for focus/hidden states.
- **ElementInternals:** `attachInternals()` can only be called once per element. Components that need form participation, custom states (`:state()`), or `ElementInternals`-based ARIA must apply `withInternals()` and read `this.internals` — never call `this.attachInternals()` directly (see `src/docs/mixins/withInternals.md`). Most display-only components don't need it.
- **Custom Events:** Dispatch events as typed `Event` subclasses from `src/events/`, not a generic string-keyed `emit()` helper. One file per event, named `{owner}-{event}.ts` (e.g. `button-click.ts`) so names stay collision-free as more components add events. Each class hardcodes its own `bubbles`/`cancelable`/`composed` and augments `GlobalEventHandlersEventMap` so listeners get a typed `event.detail` for free:
  ```ts
  export class ClickEvent extends Event {
    readonly detail: { originalEvent: MouseEvent };
    constructor(detail: { originalEvent: MouseEvent }) {
      super("u-click", { bubbles: true, cancelable: false, composed: true });
      this.detail = detail;
    }
  }
  declare global {
    interface GlobalEventHandlersEventMap {
      "u-click": ClickEvent;
    }
  }
  ```
  Dispatch with `this.dispatchEvent(new ClickEvent({ originalEvent: e }))`.

## Workflows

- **Development:**
  - Start dev server: `npm run dev` (Vite server on localhost)
  - Build library: `npm run build` (runs tsc then vite build → ES module in dist/)
  - Preview build: `npm run preview`
- **Storybook:**
  - Start Storybook: `npm run storybook` (port 6006)
  - Build Storybook: `npm run build-storybook`
  - Tests: Vitest automatically runs `.stories.ts` files in browser via Storybook addon
- **Testing:**
  - Run all tests: `npx vitest` (`unit` project: plugin tests in Node; `browser` project: `src/**/*.test.ts` in Chromium, e.g. the registry; `storybook` project: stories in Chromium, Firefox and WebKit via Playwright)
  - Setup: `.storybook/vitest.setup.ts` configures Storybook test environment
  - Browser compatibility: `npm run compat` (es-check on `dist/`, doiuse on CSS) and `npm run test:legacy` (builds, then runs `dist/` in a real Firefox ESR 115)
- **Linting & Formatting:**
  - Lint: `npm run lint` (oxlint, auto-fixes issues)
  - Format check: `npm run fmt:check` (oxfmt)
  - Format: `npm run fmt`

## Browser Support

- **Matrix:** pinned in `package.json` `"browserslist"` (Chrome/Edge ≥ 111, Firefox ≥ 115 ESR, Safari/iOS ≥ 16.4). It feeds `build.target`/`build.cssTarget` and `npm run compat`. Versions are pinned on purpose (a rolling query would silently drop browsers); next review March 2027, when Firefox ESR 115 ends. Details: [Browser Support](src/docs/architecture/browser-support.mdx).
- **Before using a recent CSS/JS feature**, check it against the matrix (MDN/caniuse): `npm run compat` misses `color-mix()`, `text-wrap`, `::backdrop` inheritance, `:state()` and nested at-rules.
- **`:state()` is an enhancement only:** `customStates` is a no-op on Chrome 90–124, Firefox < 126 and Safari < 17.4 — reflect an attribute too when the state matters for rendering.
- **`::backdrop` inherits nothing** before Chrome 122 / Firefox 120 / Safari 17.4: never rely on custom properties alone there (documented literal-fallback exception in `modal.css`).
- **CSS nesting** is fine in sources (Lightning CSS flattens it at build time).

## CSS Architecture & Layer Organization

- **Cascade Layers:** CSS organized into layers with explicit priority: `reset > tokens > base > components > utilities > shame`
- **Main Entry:** `src/styles/main.css` imports layer files and declares layer order
- **Token Pattern:** Each token file declares its own `@layer tokens.{name}` block (self-documenting approach):
  ```css
  /* src/styles/tokens/color.css */
  @layer tokens.color {
    :root {
      --u-color-primary: hsl(210, 100%, 50%);
    }
  }
  ```
  Then `src/styles/layers/tokens.css` imports without `layer()` function and declares sub-layer order:
  ```css
  @import "../tokens/color.css";
  @import "../tokens/spacing.css";
  @import "../tokens/typography.css";
  @layer tokens.color, tokens.spacing, tokens.typography;
  ```
  This avoids nested layer syntax errors during minification.
- **Reset & Utilities:** Provides baseline styles and helper classes (e.g., `.visually-hidden`)
- **Shame Layer:** For emergency `!important` overrides only — must be documented with issue/ticket reference
- **Token Prefix:** every token, at all three tiers, starts with `--u-` (ADR 0001, D4): no collisions with host apps, same names for every brand. Component tokens are named `--u-<component>-<css-property>[-<state>]`, where `<component>` is the tag name without its prefix (`button` for `u-button` or a brand's `acme-button`).
- **Three-Tier Tokens:** primitive (`tokens/color.css`, etc.) → semantic (`tokens/semantic.css`, intent-based aliases like `--u-color-action-bg`) → component (`--u-button-background-color`, declared on `:host`, defaulting to a semantic token — never a literal). Components must not hardcode colors/spacing/radius/motion; see [CSS Architecture Documentation](src/docs/architecture/css-architecture.mdx) for the full pattern.

## Conventions & Key Points

- **No Lit Bundling:** Lit is `external` in `vite.config.ts` and a **peer dependency** (ADR 0001, D6): the brand design system or the app provides the single copy of Lit. It stays in `devDependencies` for local work.
- **Aliases:** Use `@/` for `src/` imports (configured in `vite.config.ts`).
- **Strict TypeScript:** Strict mode enabled; follow type safety rigorously.
- **Accessibility:** Use `a11y` Storybook addon; tests run via vitest in real browser.
- **Component Exports:** Only export public components from `src/index.ts`.
- **Storybook MDX Docs:** Storybook's MDX has no GitHub-flavored Markdown — write tables in HTML (`<table>`), never pipe tables (they render as raw text). See `.claude/skills/storybook-documentation/SKILL.md`.
- **Build Output:** `npm run build` regenerates the manifest, then produces ES modules in `dist/` (CSS inlined in the JS, global `styles.css`), the `.d.ts` files, the compiled Vite plugin (`dist/plugins/`, from `tsconfig.plugin.json`) and `dist/css-modules.d.ts`.
- **Package Surface (ADR 0001, D6):** `exports` lists `.` (side-effect free: components, `DSBaseElement`, mixins, events, types, `defineComponents`, `allComponents`), `./define` (registers the `u-` catalog), per-component entries, `./styles.css`, `./custom-elements.json`, `./vite-plugin` (the CSS module scripts plugin, for brand design systems; `vite` is an optional peer dependency) and `./css-modules` (types for `import sheet from "./x.css" with { type: "css" }`). `sideEffects` only lists CSS and `dist/define.js`: any new module with import-time side effects must be added there. Validate the package with `npx publint` and `npx @arethetypeswrong/cli --pack . --profile esm-only`.
- **Component Styles:** Each component/mixin keeps its styles in a sibling `.css` file, imported as a CSS module script and appended to `static styles` after the inherited ones — never inline Lit `css` tagged templates:
  ```ts
  import alertStyles from "./alert.css" with { type: "css" };
  // ...
  static styles = [DSBaseElement.styles ?? [], alertStyles];
  ```
  The default export is a constructable `CSSStyleSheet` (typed in `src/css-modules.d.ts`). `plugins/css-import-attributes.ts` makes this work in Vite, Storybook and Vitest (`vitest.config.ts` merges `vite.config.ts`), and inlines the minified CSS into the built JS, so consumers need no CSS-import support. Don't use a default import of a `.css` file without `with { type: "css" }`, and don't import the global `src/styles/` sheets this way — those are document-level, not shadow-DOM, styles. The plugin errors on such misuse (value import without the attribute, dynamic `import()` of a CSS module) and fails the build if any `.css` import is left in the shipped JS (Safari has no CSS module scripts).
  **When Vite supports `type: "css"` natively** (vitejs/vite#18534): delete the plugin, check that the build output still has no `.css` imports (keep the `findUncompiledCssImports` check), and drop `src/css-modules.d.ts` if `vite/client` types these imports.
